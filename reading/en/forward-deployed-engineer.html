The Engineer Next to the Problem

Why does a colleague fix the same order file by hand every morning? An engineer working alongside her can find out, try a fix on the job and leave the team able to maintain it.

IN THIS EXPERIENCE

  • Before writing a script, watch an order specialist and ask why she edits a row by hand.
  • Give a colleague a fresh file and see if they can tell when a parcel should be held.
  • Before the builder leaves, establish who will fix the tool if an export column changes.

What changes when engineering sits beside the work?

Every morning an order specialist downloads a file, moves a few rows and retypes a number. From across the room, a short script sounds like the answer. Sit beside her and one row might turn out to be a cancellation, another a customer who just changed address. You need to know why she makes those edits before teaching software to repeat them.

A forward-deployed engineer, often called an FDE, builds alongside the people who will use the result, inside their own systems. That’s how McKinsey describes the role, and Palantir’s job description also emphasizes working directly with customers. In our example, the engineer’s work should be testable on the morning file. The job title alone tells you little about how long the project will take.

What should this stage deliver?

Understand

A problem you can examine

Ask the specialist to work through an approved file the usual way and explain each pause. Perhaps she’s waiting for confirmation of a new address. By the end, both of you should recognize the same problem statement, such as “An amended order looks exactly like the old one in the export.”

Build

The smallest usable path

For a first build, follow one amended order from the file to the dispatch list. The engineer might show the latest update time beside the address. Using that view, the specialist should be able to decide whether to release the order or call the customer first.

Handover

Work the team can continue

Ask a different colleague to handle a fresh case tomorrow. If there are two addresses, how will they know which one is valid? If the file won’t open, who gets called? The point where that colleague gets stuck tells you what is still missing from the handover.

What has a good demo left unproven?

A demonstration on a tidy file may go beautifully. At handover, give the specialist the keyboard and a different case. Can she recognize a questionable address, hold the parcel and explain why to the warehouse? You can judge the tool by what the next person was actually able to do.

What if the tool is specific to this customer?

A tool that fits only this company’s export might suit the team perfectly. Write down what happens if a column is renamed or the address format changes, who will notice and whose time pays for the fix. That conversation is much easier while the engineer is still available.

The engineer must see the problem in the real system

The written procedure may say only “send the order file to the warehouse.” It won’t show the short call the specialist makes to confirm a new address. Working from the document alone, an engineer might simply deliver the old address faster. Sitting with the specialist gives the engineer a chance to catch that difference before building.

Observing the work doesn’t mean opening every customer record. Choose a case the team has permission to review. Look at the fields needed to understand that pause, then describe what you saw to the person receiving the parcel. The warehouse colleague might point out that the address gets checked a second time elsewhere.

How is this different from a consultant?

Companies draw the line between this role and consulting in different places. McKinsey’s interview describes it as evolving. For a hiring decision, ask a more concrete question. Who builds in your environment, who tries the result on the job and when does the person who will maintain it take over?

The first delivery should remove a real obstacle

Now there’s a small piece worth building. On the screen that releases orders to the warehouse, show the current address beside its last update time. If it changed after the label was printed, the specialist knows which parcel to hold. Try that change and watch whether she still has to search through several screens.

Agree on what to look for before the demonstration. An ordinary order should go through to dispatch. One with conflicting addresses should wait for review. If you only try the ordinary case, you still don’t know how the tool handles the very exception that brought the engineer to the warehouse.

Compare an earlier case with one handled using the new tool. What evidence did the specialist used to consult for the right address? Where is it now, and how would she spot a problem with it?

The capability must remain in the organisation

At handover, ask a second person to process a case and investigate a small fault without the builder’s help. They need to know where the address comes from, where doubtful orders go and who maintains the tool. If they still have to message the engineer to decipher a column, explaining that column belongs on the remaining work list.

Once you understand the work, you might find an existing product already handles it. Or the warehouse might have a few rules that make a custom build worthwhile. Weigh the cost of running and maintaining each option against what the specialist could actually accomplish. That comparison gives the team a practical reason to choose.

Write a short engagement brief

When drafting an engagement brief, start where an order gets stuck on someone’s desk. Say who takes it from there, which records they’re allowed to inspect and which exception they should be able to handle after the engineer leaves. An approved sample file and agreement on that test give the first meeting a job to do.
